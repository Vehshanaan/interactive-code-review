# Interactive Code Review

目标是帮助读者建立对代码的准确、连贯且足以支持自主判断的理解，而不是代替读者 review 代码，也不是单纯生成技术文档。

以一份持续演化的导读文档承载 review 成果：先建立整体理解，再由读者通过阅读、提问和批注决定需要进一步解释的部分，直到读者认为足以满足当前目的。文档既是交互的媒介，也是交互的产物。文档的生命周期由读者决定，内容由读者与 Agent 共同演化。

## 1. 确定工作文档

同一 review 过程应持续维护同一份导读文档。调用本 Skill 本身不构成新建或重写文档的指令。

- 确定 review 对象与范围，可以是文件、模块、代码变更、整个项目或某个行为。
- 若用户已指定工作文档，或当前上下文能够明确确定正在使用的文档，直接读取最新版本并继续，无须重复确认。
- 若无法确定工作文档，先询问用户是继续已有文档，还是新建导读。可以提供发现的候选文档。
- 仅在用户明确要求新建，或确认不存在需要继续维护的文档后，才创建新文档。未找到已有文档不代表其不存在。
- 除非用户明确要求从头重写，否则以已有文档为基础进行增量修订，保留此前积累的有效解释、读者反馈及未解决的问题。必要的局部重写和结构调整不受此限制。

工作文档确定后，后续调用默认延续该文档，直至用户主动切换或结束 review。新建文档进入初始导读；继续已有文档直接进入迭代 review，不重复初始化。

## 2. 建立初始导读

阅读相关源码，建立帮助读者理解代码整体逻辑的文档。

- 先解释代码解决什么问题、整体如何工作、各部分如何关联。
- 根据代码性质选择最合适的叙述结构，包括调用关系、数据流、状态转换、数据结构、算法或设计约束，不强制固定模板。
- 阅读代码变更时，解释变更前后的行为差异及其影响。
- 初稿以建立整体理解为主，不默认逐行讲解或填满实现细节。保留影响判断的重要条件、假设和异常路径。
- 关键结论应有可追溯的源码位置或符号。按需使用图、伪代码、例子。

将初稿写入工作文档并告知位置。首次交付时，简要说明：读者可以直接在文档中批注，也可以在对话中提问、质疑结论或陈述理解。Agent 将核对源码并把澄清融入同一份文档。

交付初稿后，将主动权交还读者，不自行展开无休止的细化。

## 3. 迭代 review

每轮收到读者反馈时：

1. **读取最新文档。** 识别疑问、质疑、理解偏差和尚未处理的批注。接受文档与对话中的反馈，不要求特定语法。
2. **回到源码核实。** 追查相关实现、上下文及依赖，不仅依据上一版解释作答。区分源码可以证实的事实、设计意图推断和需要运行或其他证据才能验证的结论。发现潜在缺陷时，呈现证据、影响和未决问题。
3. **消除理解缺口。** 按反馈决定补充细节、解释前置知识、改变抽象层级、提供例子或重新组织叙述。提问既是待回答的问题，也是调整文档颗粒度的反馈。
4. **将澄清融入原文档。** 就地补充细节、改写解释、纠正错误或重组章节，不机械追加问答记录。局部发现影响整体理解时，同步修订上层叙述及源码引用。默认写回有价值的澄清，除非读者明确要求仅讨论。
5. **交还文档。** 保留未解决的问题及有效批注。仅按读者认可的约定清理已解答的临时批注。简要告知更新位置及仍待确认的问题，随后由读者继续 review。

重复循环，直到读者主动结束或改变任务。

## 4. 文档演化原则

### 颗粒度自适应

不预设读者知识水平，不要求各章节解释深度相同。根据实际反馈调整深度、广度、前置知识及表达方式。已足够清楚的部分通常无需展开；读者反复遇到困难时，改变解释方式而非仅增加文字。

信息密度应是交互的自然结果，但不得因读者尚未提问而省略影响整体理解或判断的关键信息。

### 整体优先

细节服务于整体理解。保持文档连贯，使读者理解局部在整体中的作用与相互关系。新解释改变原有整体认知框架时，同步修订相关内容，避免细节累积破坏主线。

### 源码为准

描述实际实现而非想象的设计。核实读者的假设，不迎合读者而将其写成事实。代码变化时核对受影响的解释并修正过时结论。明确标示不确定内容。

### 成果持久化

将有长期价值的澄清融入正文，使文档脱离对话历史和已解答批注后仍能独立阅读。保护此前积累的有效认知成果，不为了统一格式、调整风格或重新生成看似完整的文档而丢失解释。

以最新文档和源码为后续会话的依据，而非依赖 Agent 记忆。

### 读者主导

读者决定关注点、理解的充分程度以及文档生命周期。Agent 可以主动指出重要信息，但不擅自扩大范围或追求不必要的细节。篇幅、深度和覆盖率不是独立的完成指标；目标是支持读者的理解和自主判断。

## 5. 环境适配

不依赖特定编辑器、Agent、工作区目录、版本控制系统、批注语法或文档载体。

- 获准新建时优先使用用户指定的载体及位置，否则遵循项目约定或选择合适的独立 Markdown 文件，并告知位置。
- 继续已有文档时，沿用载体、语言和有价值的结构，不为自身方便而迁移或重新生成。
- 直接处理可读取的批注；无法读取时，接受对话中的相关段落及问题。
- 缺少必要源码时请求路径或片段，不编造实现。
- 无法直接写入时，交付完整初稿或可明确应用的修订内容，说明未实际写入，让读者自行保存并在下一轮提供最新版本。

环境适配应服务于核心工作流程，不改变持续演化的机制。

## 6. 边界与结束

默认只修改工作文档，不修改被 review 的源码。源码修改、提交和发布由用户另行明确授权。

结束时确保当前文档包含已获得的澄清，并明确未解决或未经验证的问题。不额外生成总结或不必要地重写已有文档。

理解代码不等于验证正确性，不将结束 review 表述为代码通过审查。

已经结束的 review 可以在后续会话中重新开启，使用原工作文档及相关源码，从已有认知成果继续。
